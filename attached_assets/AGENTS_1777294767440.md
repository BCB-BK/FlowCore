# AGENTS.md — Senior-Engineer-Vertrag für KI-Agenten

> **Diese Datei ist verbindlich.** Sie wird vor jeder Sitzung geladen und gilt für jeden KI-Agenten, der in diesem Repository arbeitet (Replit Agent, Cursor, Aider, Claude Code, …). Verstöße sind kein "Fehler", sondern ein Vertragsbruch.

## Kontext

Dieses Projekt ist ein produktiv eingesetztes Research-Tool (Deutsch). Der Auftraggeber ist Nicht-Programmierer. Er kann Code nicht prüfen, aber Logik. Wenn der Agent oberflächlich arbeitet, fällt es ihm im operativen Betrieb auf die Füße — und kostet stundenlange Reparatur-Sitzungen. Auslöser dieses Dokuments war der DEV→PROD-Snapshot-Bug vom 2026-04-26 (Commit `e0ea082` → Korrektur `37a6e34`): ein automatischer `prebuild`-Hook hat den committeten Snapshot im PROD-Build überschrieben — der Agent hat zwei "Fix"-Anläufe gestartet, ohne die Lifecycle-Hooks zu auditieren. Das passiert nicht mehr.

## Die acht Regeln

### R1 — Pre-Action-Audit-Pflicht

Bevor du Code an einer Schnittstelle änderst (Snapshot, Bootstrap, Pipeline, DB-Schema, Build-Konfig, Deployment-Konfig), kartierst du:

- **Alle Schreib-Pfade** auf das betroffene Artefakt (`rg`-basiert, nicht "ich glaube").
- **Alle Trigger** (Cron, Lifecycle-Hook, postinstall, prebuild, postBuild, husky).
- **Alle Lesepfade** (wer importiert was?).
- **Alle ähnlich-benannten Dateien** (Snapshot vs. Snapshot-Diff vs. Snapshot-Backup).

Das Audit-Ergebnis kommt **als Tabelle** in deine Antwort an den User, **bevor** du editierst. Nicht "das hab ich im Hinterkopf" — sichtbar.

**Negativ-Beispiel (was passiert ist):** Snapshot-Bug wurde mit "Setze `REPLIT_DEPLOYMENT`-Check ein" geantwortet, ohne zu prüfen, ob `REPLIT_DEPLOYMENT` im Replit-Build überhaupt gesetzt wird (war nicht). Drei Anläufe nötig.

**Positiv-Beispiel:** 8-Schichten-Audit (Schreibstellen, Trigger, Lifecycle-Hooks, .replit, artifact.toml, husky, build.mjs, .gitignore) als Tabelle in der Antwort, **dann** Fix.

### R2 — Empirie vor Antwort

Aussagen über Laufzeit-Verhalten sind nur erlaubt, wenn du sie empirisch verifiziert hast:

- "Es funktioniert" → **nur** nach Logs-Lesen (`refresh_all_logs`) oder Counts-Query.
- "PROD ist heil" → **nur** nach PROD-DB-Query oder PROD-Logs-Fetch (`fetch_deployment_logs`).
- "Der Test besteht" → **nur** nach Skript-Lauf, nicht nach Code-Review.

Verboten: Hoffnung, Plausibilität, "müsste eigentlich". Wenn du keine empirische Verifikation hast, sagst du das explizit: "Ich habe X nicht verifiziert."

**Negativ-Beispiel:** "Der Snapshot wird vermutlich beim Deploy korrekt geladen." — keine Quelle, keine Verifikation, reine Hoffnung.

**Positiv-Beispiel:** "Snapshot ist im Build embedded. Belegt durch `pnpm --filter @workspace/api-server run build && stat -c %s artifacts/api-server/dist/...` → 4'782'842 Bytes, generatedAt=2026-04-26T19:20."

### R3 — Anti-Hedge

Hedging-Sprache ist verboten für Aussagen, die empirisch verifizierbar sind:

| ❌ Verboten | ✅ Stattdessen |
|---|---|
| "Es greift vermutlich nicht in Build" | "Ich habe geprüft: `REPLIT_DEPLOYMENT` ist im Build nicht gesetzt — Beweis: `printenv` zeigt …" |
| "Sollte funktionieren" | "Funktioniert. Verifiziert via …" |
| "Müsste eigentlich" | "Ist. Belegt durch …" |
| "Falls noch ein anderer Mechanismus existiert" | "Audit zeigt: kein anderer Mechanismus existiert. Geprüfte Kanäle: A, B, C." |
| "Ich denke, das" | "Geprüft: …" / "Nicht geprüft: …" |

Wenn du wirklich unsicher bist (echtes Nicht-Wissen), benenne die konkrete Wissenslücke: **"Was ich nicht weiß: X. Was ich tun müsste, um es zu wissen: Y."** Das ist OK. Vage Phrasen sind nicht OK.

Der `anti-hedge-check`-Validator scannt neue Code-Kommentare auf Hedging-Vokabular und blockt den Commit. Für deine Antworten an den User gilt dieselbe Disziplin freiwillig.

### R4 — E2E statt DB-Manipulation

Wenn der User sagt "teste das Feature", heißt das:

- ✅ Browser/Frontend bedienen (über das Testing-Skill: `runTest`).
- ✅ Komplette HTTP-Request-Kette inklusive Auth, Pipeline, DB-Persistenz, Frontend-Rendering.

Nicht erlaubt:

- ❌ Direkte SQL-Queries als "Test" (das ist Inspektion, kein Test).
- ❌ Direkte API-Calls mit `curl` als alleiniger Test (umgeht Frontend-Logik).
- ❌ DB-Inserts, um einen "Erfolg" zu fingieren.

Wenn ein E2E-Test gerade nicht möglich ist (Auth blockiert, externe API down, …), erklärst du das **explizit** und schlägst einen Follow-up-Task für späteren E2E-Test vor.

### R5 — Snapshot-Frische vor Deploy

Vor jedem `suggest_deploy`-Vorschlag oder PROD-Deploy-Diskurs **musst** du `pnpm run pre-deploy-check` laufen lassen. Es vergleicht den committeten `config-snapshot.json` gegen die DEV-DB:

- Counts pro Strict-Mirror-Tabelle (`streams`, `stream_sources`, `stream_recipients`, `stream_coverage_rules`, `schedules`).
- Stream-Slug-Set (welche Slugs in DB aber nicht in Snapshot? → Re-Export nötig).

Bei Drift → kein Deploy-Vorschlag, sondern: "Snapshot ist X Streams alt — bitte `pnpm --filter @workspace/api-server run export-snapshot` laufen lassen und Snapshot mitcommitten."

**Negativ-Beispiel:** "Lass uns deployen, ich habe drei neue Streams in der DEV-DB angelegt." — Snapshot wurde NICHT re-exportiert, drei Streams kämen nie in PROD an.

**Positiv-Beispiel:** "Drei neue Streams in DEV-DB. `pnpm run pre-deploy-check` zeigt Drift (Snapshot=34, DEV-DB=37). Re-Export läuft jetzt: `pnpm --filter @workspace/api-server run export-snapshot` → Snapshot enthält jetzt 37 Streams. Committet als `<sha>`. Erst jetzt deploy-bereit."

### R6 — Senior-Self-Review vor `mark_task_complete`

Vor jedem `mark_task_complete` führst du `pnpm --filter @workspace/scripts run senior-self-review` aus, **füllst die Antworten aus** und fügst sie als Markdown-Block in deine letzte User-Antwort ein. Sechs Felder:

1. **Gelesene Dateien** (Pfade).
2. **Geänderte Dateien** (Pfade + 1-Zeilen-Begründung pro Datei).
3. **Referenz-Suche** (`rg`-Befehl + Zeilen-Anzahl: was importiert/nutzt das Geänderte?).
4. **Root-Cause-Beleg** (warum ist das die Ursache und nicht ein Symptom?).
5. **Empirische Verifikation** (welche Logs/Counts/E2E-Läufe belegen den Erfolg?).
6. **Floskel-Selbstkritik** (welche Hedging-Phrase in meiner Antwort hätte ein Skeptiker bemängelt? Wenn keine: "Keine Hedging-Phrase verwendet.").

Ohne diesen Block ist die Aufgabe nicht "fertig". Punkt.

**Negativ-Beispiel:** "Habe alles erledigt, validate ist grün, mark_task_complete." — kein Self-Review-Block, keine Empirie-Belege, keine Drift-Reflektion.

**Positiv-Beispiel:** Senior-Self-Review-Markdown-Block mit allen 6 Feldern ausgefüllt + zitiert in der User-Antwort, gefolgt von `mark_task_complete` mit `drift_reason`.

### R7 — Single-Source-of-Truth-Disziplin

| Bereich | SSOT | Verbot |
|---|---|---|
| Konfigurations-Daten (Streams, Quellen, Schedules, Settings) | `config-snapshot.json` + `seed-allowlist-overrides.ts` + `connector-soll-state.ts` | Hardcoded Slugs/URLs/Counts in Business-Logik |
| Environment-Variablen | `src/config.ts` (zentral) | `process.env.X` ausserhalb Config-Modul |
| Institutsnamen, Domains | `src/lib/bcb-entities.ts` (oder analog) | Inline-Strings wie `"BildungsCampus Backnang"` |
| Reason-Codes (Discard, Reject) | `lib/db/src/discard-reasons.ts` | Frei erfundene Codes pro Endpoint |
| AI-Prompt-Bausteine | Dedizierte Prompt-Module | Inline-Prompt-Strings in Business-Code |

Bei Konflikt zwischen DB-Stand und SSOT-Datei: **SSOT-Datei gewinnt.** DB-Stand wird beim nächsten Boot vom Bootstrap-Mirror überschrieben (für Strict-Mirror-Tabellen) oder vom Override-Skript korrigiert (für Keyword-Groups, Allowlists).

### R8 — Root-Cause vor Symptom

Wenn ein Test rot ist oder ein Feature nicht funktioniert:

1. **Erst:** Warum (mechanistisch — welche Funktion liefert was, welche Bedingung trifft nicht zu, welcher Aufruf läuft anders als erwartet)?
2. **Dann:** Welcher minimale Eingriff korrigiert die Ursache?
3. **Verboten:** Try/catch um den Fehler herum, `?.`-Optional-Chains als "Fix", Test-Skip, Feature-Toggle off.

**Negativ-Beispiel:** Optimizer sendet `null` für `affectedEntity` → Schema sagt `.optional()` → Validator wirft. **Symptom-Patch:** Validator-Aufruf wegmachen. **Root-Fix:** Schema auf `.nullish()` ändern, weil OpenAI-Responses-API tatsächlich `null` sendet (nicht `undefined`).

**Positiv-Beispiel:** Pipeline failed mit "Cannot read property of undefined". Statt `?.`-Chain dranzukleben: `git blame` zeigt, dass die Property in einem Refactor entfernt wurde. Root-Fix: Property im Refactor mit migrieren oder den entsprechenden Code-Pfad sauber entfernen, nicht stillschweigend tolerieren.

Wenn du eine Symptom-Behandlung machen **musst** (z.B. weil der Root-Fix in einer anderen Codebase liegt), kennzeichne sie explizit als Workaround mit Verweis auf den eigentlichen Fix-Pfad.

## Wie du diese Datei liest

Du liest `AGENTS.md` **bei jeder neuen Sitzung als allererstes** — vor `replit.md`, vor allem anderen. Wenn du sie nicht gelesen hast, hast du den Vertrag nicht akzeptiert. Bei Konflikt zwischen Skill-Hinweisen und `AGENTS.md` gewinnt `AGENTS.md`.

## Was passiert bei Verstößen

Der User wird Vertragsbrüche namentlich nennen ("Du hast R1 verletzt — kein Audit-Tabellen-Output vor dem Edit"). Das ist kein persönlicher Angriff, sondern eine Diagnose. Reaktion: Vertragsbruch anerkennen, korrektes Verhalten nachholen, weitermachen.

## Verifikations-Workflow am Ende einer Sitzung

```
1. pnpm run validate           # alle 11 statischen Checks (siehe replit.md)
2. pnpm run pre-deploy-check   # Snapshot-Frische
3. pnpm --filter @workspace/scripts run senior-self-review  # Selbst-Audit
4. → Audit-Block in User-Antwort einfügen
5. → mark_task_complete
```
